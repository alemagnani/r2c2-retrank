**Team:** retrank

**Submitted runs:** retrank-PG-1, retrank-PG-2, retrank-PG-3, retrank-PG-4

---

## 1. Task & Corpus

The R2C2 Passage Retrieval task requires retrieving and ranking passages (≤200 characters each) from an IMDb-like corpus (Wikipedia + Wookieepedia movie articles) for 65 natural language questions about films. Evaluation metric: **nDCG@20**.

Two submission routes:
- **PO** — using organizer-provided passage segmentation
- **PG** — using own passage segmentation

All submitted runs use **PG** (own passages), as they consistently outperformed organizer passages in internal evaluation.

---

## 2. Corpus & Passage Segmentation

### 2.1 Organizer passages (PO route)
The organizer provides pre-segmented passages. Initial experiments used these for BM25 baseline runs, but performance was capped by the organizer's fixed segmentation.

### 2.2 Own passages (PG route)
We reconstructed full document texts from the organizer's passage metadata and applied a **sliding-window segmentation**:

- **Window size:** 200 characters (hard cap, matching submission constraint)
- **Stride:** ~16 words (~100 characters)
- **Minimum length:** 50 characters
- **Deduplication:** adjacent identical windows removed

**Result:** 2,529,673 passages from 551,653 documents.

This approach ensures maximum coverage: every possible ≤200-char span of every document is indexed, eliminating blind spots from fixed sentence or paragraph boundaries.

---

## 3. Retrieval & Reranking Pipeline

The final pipeline has three stages:

```
BM25 (own passages) → Cross-Encoder Reranker → Diversity Selection → top-20
```

### Stage 1: BM25 First-Stage Retrieval
- **Library:** BM25S (fast BM25 implementation)
- **Tokenization:** lowercase, alphanumeric tokens, stopword removal, min length 2
- **No stemming** (tested but did not improve results)
- **Pool sizes tested:** 50, 100, 200, 500 candidates per topic

### Stage 2: Cross-Encoder Reranking
- **Model:** `cross-encoder/ms-marco-MiniLM-L-12-v2`
- **Input:** (query, passage) pairs, max 512 tokens
- **Batch size:** 128
- All candidates from Stage 1 are scored

### Stage 3: Diversity Selection
Three strategies evaluated:
- **topk** — straight top-20 by CE score, no diversity
- **overlap** — Jaccard diversity filter: skip a passage if Jaccard overlap with any already-selected passage exceeds threshold; cap passages per document
- **mmr** — Maximal Marginal Relevance: iteratively select passage maximizing `λ·CE_score - (1-λ)·max_similarity_to_selected`

---

## 4. Evaluation Methodology

### 4.1 Synthetic validation set
Since official qrels are not released until after submission, we built an independent validation set:

- **Source:** 1,300 synthetic topics generated by Claude Haiku, covering 24 challenge types (plot_detail, actor_identity, multi_hop, vocabulary_gap, etc.) about movies not in the real R2C2 topic set
- **Val250:** stratified sample of 248 topics (seed=42), excluding any overlap with real topics
- **Purpose:** unbiased proxy metric for all architecture decisions

### 4.2 LLM-as-judge evaluation
We use Claude (Haiku for sweep, Sonnet for final selection) to evaluate each run:

**Prompt design:** All 20 retrieved passages are sent in a single call. The model:
1. Counts **unique nuggets** — distinct atomic facts relevant to the question, deduplicated across all 20 passages
2. Grades each passage **0–3** (not relevant → highly relevant)
3. Computes nDCG@20 from the grades

**Why this works as a proxy:** Nugget count directly penalizes redundancy — three near-identical passages from the same document count as one nugget. This creates pressure toward diversity in selection strategies, matching the spirit of nDCG@20 evaluation.

**Cache:** Results cached by SHA256(topic_id + ordered passage texts), shared across runs. Total judgments: ~3,200 Haiku + ~1,500 Sonnet.

## 5. Phase 1: Baseline Experiments (Organizer Passages)

Early experiments using organizer passages with BM25 + CE established:
- Jaccard overlap diversity (threshold=0.5, max 3/doc) outperformed topk selection
- The "td100" configuration (BM25 top-100, CE reranked, overlap) was the best baseline

These runs were submitted as **PO-1** in the initial submission. After the deadline extension, we pivoted to own passages for all subsequent work.

## 6. Phase 2: Retrieval Architecture Sweep (Own Passages)

### 6.1 Conditions tested (Haiku eval, 248 topics)

Nine conditions: {BM25, Dense, Hybrid} × {pool 50, 100, 200}, CE reranked with topk selection.

| Run | Nuggets | nDCG@20 | Notes |
|---|---|---|---|
| bm25_200_topk | 2.976 | 0.787 | **Best** |
| bm25_50_topk | 2.923 | 0.792 | |
| bm25_100_topk | 2.891 | 0.767 | |
| hybrid_100_topk | 2.968 | 0.769 | BM25+dense RRF |
| hybrid_200_topk | 2.915 | 0.777 | |
| dense_200_topk | 1.722 | 0.478 | **Far worse** |
| dense_100_topk | 1.621 | 0.448 | |
| dense_50_topk | 1.323 | 0.435 | |

**Finding:** BM25 dominates. Dense retrieval (bi-encoder `msmarco-MiniLM-L6-cos-v5`) performs dramatically worse on this movie corpus. Hybrid degrades vs pure BM25 because RRF introduces weak dense signal.

### 6.2 Why dense retrieval fails

The `msmarco-MiniLM-L6-cos-v5` model was trained on MS MARCO web documents. Movie corpus passages contain:
- Named entities (character names, film titles, actor names) that dense models map to wrong embedding neighbourhoods
- Domain-specific vocabulary (production terms, award names) poorly represented in MS MARCO
- Short passages (≤200 chars) that provide little context for semantic embedding

BM25 handles exact-match and named-entity lookup much better at this scale.

### 6.3 Dense retrieval fine-tuning attempt (LoRA)

We attempted to domain-adapt the bi-encoder via LoRA fine-tuning.

**Data generation:** 519 training triplets generated by Claude Haiku:
- For each sampled movie article, Haiku generates a question + identifies the verbatim positive passage from sliding-window segments
- Haiku suggests confusable movies (same genre/era/director); we look these up in the corpus to extract hard negatives (65% hit rate)
- Remaining triplets use intra-document hard negatives (passages from same article that don't answer the question)
- 24 challenge types, weighted toward vocabulary_gap, implicit_entity, multi_hop

**LoRA configuration:** r=16, alpha=32, target modules q+v in all 6 attention layers, ~147K trainable params (0.64% of 22M total)

**Training:** 3 epochs, batch=32, MultipleNegativesRankingLoss with hard negatives, ~7 min on CPU

**Result:**

| Run | Nuggets | nDCG@20 | Notes |
|---|---|---|---|
| Base dense (pool-200) | 1.722 | 0.478 | |
| LoRA dense (pool-200) | 1.710 | 0.489 | No improvement |
| LoRA hybrid (pool-500) | 2.980 | 0.776 | Apparent win |
| BM25-500 only (fair comparison) | 2.919 | 0.787 | |

**Conclusion:** LoRA did not improve dense retrieval meaningfully (1.722 → 1.710, within noise). The apparent hybrid "win" (2.980 nuggets) was entirely attributable to the larger BM25-500 pool, not the LoRA dense component — confirmed by running BM25-500 alone (2.919). We abandoned this direction.

**Why LoRA failed:** 519 triplets are likely insufficient. The bi-encoder architecture may also not be the right inductive bias for sub-200-char passage retrieval from named-entity-rich text. Future work could explore: (a) much more training data (>5K examples), (b) ColBERT-style late interaction, or (c) a model pre-trained on Wikipedia/movie domain data.

## 7. Phase 3: Selection Strategy Sweep (Sonnet eval, 248 topics)

Using BM25-200 and BM25-500 pools, we evaluated five selection strategies against the topk control using Sonnet as judge for higher accuracy.

| Run | Pool | Selection | Parameters | Nuggets | nDCG@20 | Zero |
|---|---|---|---|---|---|---|
| bm25_500_overlap | 500 | Jaccard overlap | t=0.5, max/doc=3 | **3.129** | 0.762 | 19/248 |
| bm25_200_mmr | 200 | MMR | λ=0.7, max/doc=3 | 3.117 | **0.767** | 22/248 |
| bm25_200_overlap | 200 | Jaccard overlap | t=0.5, max/doc=3 | 3.097 | 0.774 | 25/248 |
| bm25_200_topk | 200 | topk | — | 3.056 | 0.763 | **control** |
| bm25_200_overlap_strict | 200 | Jaccard overlap | t=0.3, max/doc=2 | 2.968 | 0.772 | 25/248 |
| bm25_200_maxdoc1 | 200 | Jaccard overlap | t=0.99, max/doc=1 | 2.948 | 0.780 | 26/248 |

### Analysis

**Diversity consistently outperforms topk.** The nugget metric penalizes redundancy (same fact in 3 passages = 1 nugget), so replacing near-duplicate passages with ones covering new facets directly improves score. topk (3.056) < overlap (3.097) < mmr (3.117) < 500+overlap (3.129).

**Larger pool + diversity (bm25_500_overlap) wins on nuggets** (+0.07 over control, fewest zero-nugget topics at 19/248). More BM25 candidates increase the chance of finding a diverse passage that covers a rare answer facet.

**MMR (λ=0.7) provides the best nDCG balance.** Unlike hard Jaccard filtering, MMR scores candidates as `0.7·CE_score - 0.3·max_sim_to_selected`. A slightly less relevant but novel passage can beat a very similar high-scoring one, producing better-calibrated ranking within the 20 passages.

**Strict dedup (t=0.3, max/doc=2) and maxdoc=1 hurt.** Forcing out passages that share >30% word overlap removes too many genuinely high-CE passages, replacing them with lower-scoring ones that happen to be lexically different. The nDCG penalty from lower-ranked relevant passages outweighs the nugget diversity gain.

**Zero-nugget topics:** bm25_500_overlap recovers answers for hard topics that BM25-200 misses, reducing zero-nugget count from 25 to 19.

## 9. Key Takeaways

1. **Own passage segmentation outperforms organizer passages.** Sliding-window with 200-char cap and ~16-word stride maximizes coverage and eliminates boundary artifacts.

2. **BM25 dominates dense retrieval on this corpus.** Named-entity-rich movie passages favor exact-match lexical retrieval. Dense bi-encoders trained on MS MARCO web text do not transfer.

3. **Cross-encoder reranking adds substantial value.** Reranking top-200 BM25 candidates with a CE improves both nugget count and nDCG significantly over pure BM25 ranking.

4. **Diversity selection is important when CE is used.** CE tends to stack multiple passages from the same document. Jaccard overlap and MMR both improve nugget count by ensuring the 20 selected passages cover different answer facets.

5. **LoRA fine-tuning on 519 synthetic triplets was insufficient** to close the dense/BM25 gap. Future work needs either significantly more training data, a different model architecture (ColBERT), or a Wikipedia-domain pre-trained model.

6. **LLM-as-judge with nugget counting is an effective development proxy** for nDCG@20 on a task with no released qrels. Nugget deduplication naturally captures information coverage, and Haiku/Sonnet judgments are consistent enough to guide architecture decisions across phases.

## 11. Note on passage length (correction)

Throughout this work we treated "≤200 characters per passage" as a hard rule from
the task. **That rule was wrong.** Re-reading the official submission instructions
post-deadline, there is no formal length cap on PR passages. The 200-char number
came from the `text_snippet` field of the organizer-delivered passage metadata,
which is a 200-char preview, not the full passage.

In practice, every other team's PR runs use passages of 1,000–2,400+ characters,
including the organizers' own reference runs (`ORG-PO-3/4`, mean ~2,327 chars).
Our 200-char sliding-window segmentation produced ~10× shorter passages than the
field, which fragmented BM25 signal across many windows of long articles and
likely contributed to lower recall on entity-relationship questions
("director of Interstellar" → entity in one sentence of an 80KB article).

We are not re-running PR — the deadline has passed — but this constraint will be
removed for any future iteration, and it does not apply to AC.

## 13. AC Task Overview

For each of the 65 questions, an AC submission must produce:

1. **An answer string** (e.g. `"Anthony Mackie"`, `"94 minutes"`)
2. **A confidence score** (0–100)
3. **A list of grounded nuggets** — atomic factual claims, each citing a passage from any team's PR run via a `(PRrunname, passage_rank)` key

Format (one record per question):
```
<D001>[AnswerString];[Confidence]
[NuggetNum];[PRrunname];[PassageRank];[NuggetText]
[NuggetNum];[PRrunname];[PassageRank];[NuggetText]
...
</D001>
```

Up to 4 AC runs allowed; ZIP as `[TeamName]-AC.zip`; deadline **May 15, 2026**.

### How AC is scored (official methodology)

Three metrics, computed by an LLM judge through a two-stage pipeline (BREV-RAG 2025 paper, §3.1):

**Stage A — Bogus Nugget Identification:** for each `(passage, nugget)` pair, the LLM decides whether the cited passage *entails* the nugget. Non-entailed nuggets are flagged "bogus" and excluded from later scoring (but counted in the precision denominator).

**Stage B — Answer Evaluation + Relevance:** given the question, our answer, and the entailed nuggets only, the LLM decides whether the answer is correct (assuming nuggets are factually correct) and which nuggets helped derive it.

**Confidence Evaluation (HMR):** pure math from per-question correctness + confidence scores.

| Metric | Definition |
|---|---|
| **Accuracy** | `correct_answers / 65` |
| **Mean Nugget Precision** | mean over questions of `relevant / total_returned` (incl. bogus) |
| **HMR** | `2·R_O·R_U / (R_O + R_U)` where `R_O = 1 - mean(conf | incorrect)` and `R_U = 1 - mean(1−conf | correct)` |

There's also a fourth, separate calculation: **PR re-evaluation** uses AC labels to re-grade PR passages (relevance grade = number of relevant nuggets contributed across all teams' AC runs), then computes nDCG@20. This is how PR submissions are scored once AC is done. Results released ~Aug 1, 2026.

### Important constraints we discovered

- **Nuggets must be entailed by their cited passage**, not verbatim. Paraphrasing/synthesis is fine if the passage logically supports the claim.
- **Stage A judges one passage vs one nugget** — each nugget must be grounded in the *single* passage it cites.
- **Stage B sees only entailed nuggets, not passages**. So nugget *text quality* matters: clean, atomic, faithful claims help the judge confirm answer correctness.
- **No formal limit on passage length** — confirmed post-PR. The "≤200 chars" rule we followed in PR was a misread (see §11).

## 16. AC Pipeline Plan

**Detailed plan**: see [`docs/AC_PIPELINE_PLAN.md`](docs/AC_PIPELINE_PLAN.md). That file is the source of truth for architecture, hypotheses, prompts, per-stage evaluation, and ablation list. This section summarises the current state.

### Architecture: answer-first + answer-conditional pool refinement + verification

Seven-stage pipeline:

1. **Stage 0 — Initial broad pool** — pick long-passage, low-overlap teams (BITEM + Error404 + WaterlooClarke); **drop retrank** because our 200-char passages are too short to be good nugget source material (see §11). Top-50 by CE per topic.
2. **Stage 1 — Candidate answer** (Sonnet) — read broad pool, propose answer + self-confidence.
3. **Stage 1.5 — Answer-conditional refinement** — re-rank broad pool conditional on the candidate answer; take top-30. Three algorithms tested (CE / Sonnet / lexical). One submitted-run pair uses NO refinement as control.
4. **Stage 2 — Targeted nugget extraction** (Sonnet) — extract atomic claims that *support* the candidate answer; each with single-passage citation.
5. **Stage 3 — Self Stage-A bogus filter** (Sonnet) — drop nuggets whose cited passage doesn't entail them.
6. **Stage 4 — Verification** (Sonnet) — derive an answer from the entailed nuggets only; compare to candidate.
7. **Stage 5 — Confidence & refusal** — combine signals; refuse when weak.
8. **Stage 6 — Format & write** — XML output via `scripts/ac_format.py`.

Each stage has its own intermediate evaluation gate (`E0.x`…`E6.x`) and an iteration loop. See plan §3.

### 4 submitted AC runs — 2×2 factorial: Stage 1.5 × Calibration

Pool source held constant: Tier-1 = BITEM + Error404 + WaterlooClarke (broad pool of 50 per topic).

| Run | Stage 1.5 | Calibration |
|---|---|---|

| retrank-AC-4 | (a) CE on `query | answer` | Variant B |

#### Stage 1.5 — Answer-conditional pool refinement (2026-05-04)

Ran all three refinement algorithms on Tier-1 pool, plus CE on the other 4 pools. Cost: ~$3 for Sonnet on Tier-1; CE ~$0 (cached); lexical $0.

**The three Stage 1.5 algorithms in detail:**

All three share the same input/output:
- **Input per topic:** broad pool of 50 passages from Stage 0 + the candidate answer from Stage 1
- **Output:** the same 50 passages, re-ranked, with the top 30 kept

What differs is the per-passage scoring function used for re-ranking.

**(a) CE on `query | answer`** — re-score each passage with the same cross-encoder we used in Stage 0, but with the question concatenated to the candidate answer as the new "query". Captures "does this passage support both the question topic and the proposed answer?" CE is a fine-tuned MS-MARCO model (`cross-encoder/ms-marco-MiniLM-L-12-v2`); free if cached, ~$0 marginal cost.

**(b) Sonnet pointwise** — for each `(topic, candidate_answer, passage)` triple, send Sonnet the prompt:
```
Question: {question}
Candidate answer: {answer}
Passage: {passage}

Rate 0–3 how strongly the passage SUPPORTS the candidate answer:
  3 = directly states the answer
  2 = strongly implies the answer (multiple supporting facts)
  1 = mentions the answer entity but does not directly support it
  0 = unrelated or contradictory
```
Sonnet returns an integer 0–3 (with one-line reasoning, discarded for ranking). We sort the broad pool by this score, take top-30. Cost: 3,250 calls per pool (50 passages × 65 topics) at ~$0.001 each ≈ $3 per pool. Caches by SHA256 of (question + answer + passage prefix).

Why this is *different* from CE: Sonnet does semantic reasoning about whether the passage actually entails the answer, not lexical overlap. A passage that says "Donnie Yen plays a blind warrior in Rogue One" entails the answer "Donnie Yen" for the JW4/Rogue-One question, but a passage that just says "Donnie Yen is a Hong Kong action star" does not. CE would weight both similarly via keyword overlap; Sonnet distinguishes them via reasoning.

**(c) Lexical answer-token bonus** — extract distinctive tokens from the answer (excluding stopwords), then for each passage compute `score = original_CE * (1 + α · |answer_tokens ∩ passage_tokens| / |answer_tokens|) + α · overlap` with α=0.5. Free, instantaneous. The intuition: passages that literally contain the answer's distinctive tokens (entity names, numbers, dates) are most likely to ground the answer.

**Tier-1 — algorithm comparison (E1.5 evals):**

| Algo | Mean overlap with broad | Top-3 oracle hit (refined / broad) | Top-10 oracle hit | Cost per pool |
|---|---|---|---|---|
| (a) CE on `q ｜ a` | 81.1% | 63/64 = 98.4% (= broad, +0) | 63/64 = 98.4% (broad: 100%, **−1**) | $0 |
| (b) Sonnet pointwise | 82.3% | 63/64 = 98.4% (= broad, +0) | 64/64 = 100% (= broad, +0) | $3 |
| **(c) Lexical** | 90.5% | **64/64 = 100% (+1!)** | 64/64 = 100% (= broad, +0) | $0 |

|---|---|---|---|---|

**Findings (RQ6 progress):**

1. **Refinement does substantial reordering** (overlap 80–91% on Tier-1 pools — i.e. ~20% of passages get re-ranked) but **does NOT measurably improve recall at top-3 or top-10** when the broad pool is already strong.

2. **The cheap lexical algorithm beats both LLM-based variants at top-3** (+1 oracle hit on topic 0059 "Samuel L. Jackson"), where CE and Sonnet tied with the broad pool. **This is a strong negative result for our hypothesis H1.5-2** that LLM-based refinement would dominate.

3. **CE refinement on Tier-1 *hurt* top-10 by 1 topic** — the (q+a, passage) CE re-scoring shuffled an answer-bearing passage out of top-10 for one question. Negative for Stage 1.5 unconditional adoption.

4. **BITEM-only barely reorders** (98.4% overlap) — single-team pools have already converged on the right docs, so the answer signal doesn't change much.

**Caveat — these evals only measure pool-level recall (E1.5-2). The real test (E1.5-3) is downstream: does refinement produce better nuggets? bogus-rate? MNP?** Possible that refinement promotes passages that *better SUPPORT the answer via reasoning* rather than just *mention the answer entity*. Stage 2 will tell.

**Decision:** keep Stage 1.5 (a) CE in the AC-2/AC-4 submitted runs as planned (RQ6a still requires downstream evaluation). The recall-level negative result is itself a paper finding for the AC-1 vs AC-2 comparison: if AC-2 doesn't beat AC-1 at HMR, it's because Stage 1.5 doesn't help; if it does, the help came from downstream effects, not pool recall.

**Surprise paper finding:** if downstream eval confirms lexical ≥ CE/Sonnet, this supports a "cheaper is better" story — answer-conditional refinement via simple lexical bonus matches LLM-based scoring. We'll know after Stage 2.

### Headline findings (paper-defining)

1. **🏆 BITEM-only pool wins decisively.** A *single*-team pool reaches HMR 0.963 — beating Tier-1 (3 teams, HMR 0.911) and Tier-1+2 (6 teams, HMR 0.874). Even more striking: BITEM-only's accuracy (0.938) is the *highest* of any configuration we tested.

2. **More teams hurts (RQ2 quantitatively confirmed).** Adding teams to BITEM degrades HMR monotonically:
   - 1 team (BITEM): HMR 0.963
   - 3 teams (Tier-1 = BITEM+Error404+WaterlooClarke): HMR 0.911 (-0.052)
   - 6 teams (Tier-1+Tier-2): HMR 0.874 (-0.089)
   - The MORE teams we add, the WORSE the AC system performs.

3. **Why does BITEM win?** Hypothesis: smaller, more focused pool → less noise in Stage 2 nugget extraction → cleaner verifier signal → fewer overconfident-wrong answers → higher R_O (0.950 vs Tier-1's 0.870). The "less is more" finding for AC: pooling is not a free lunch.

4. **Sonnet refinement still helps but only marginally on BITEM-only** (0.937 → 0.963, +0.026) compared to its big effect on Tier-1 (0.826 → 0.911, +0.085). This makes sense — when the broad pool is already focused, refinement has less to do.

5. **retrank-only is unusable** (HMR 0.838 / 0.858) because of the catastrophic Stage 1 refusal rate (29/65 = 45%). Even with a high R_O, the low accuracy and missing nuggets keep MNP at 0.42 and R_U at 0.80.

6. **retrank+Error404 with Sonnet refinement breaks** (HMR 0.738, R_O 0.595). This is the only case where Sonnet refinement *hurt* — going from 0.910 (broad) → 0.738 (refined). Worth investigating: probably the candidate answers are sometimes wrong on this pool, leading to bad refinement that misleads Stage 2.

**Finding:** by stacking Stage 1.5 Sonnet refinement + R1/R2 abstention on a weaker (Tier-1) pool, we reach HMR within 0.007–0.010 of the best (BITEM-only) pool's baseline. **Calibration machinery substantially compensates for a worse pool, but not completely.**

Why this matters for the paper: it lets us frame the choice as a trade-off:
- **Path 1 — invest in pool quality:** if you can find one strong-PG team, stop there. HMR 0.963 with a simple pipeline.
- **Path 2 — invest in calibration machinery:** if you must use a multi-team pool (e.g., constrained by what's available), Stage 1.5 Sonnet + verifier-based abstention gets you most of the way back. HMR ≈ 0.95.

This is more useful than the simple "less is more" finding alone — it says *what to do* if you can't have a single-team pool.

**Findings:**

1. **Naive RQ9 hypothesis is REJECTED.** Ensembling all 16 candidates yields HMR 0.857 — *worse* than the best single pipeline (BITEM-only at 0.963). Indiscriminate cross-pool answer ensembling hurts.

2. **But filtered ensembling helps modestly.** Top-3 (HMR 0.969) and top-1 (HMR 0.974) beat the standalone best (0.963). The lesson: the quality threshold matters — including weak pipelines (retrank_only at 0.838 HMR, tier1plus2_broad at 0.840) drags the consensus down.

3. **Refined hypothesis confirmed:** *"Cross-system diversity at the answer level helps when ensembled across high-quality pipelines, but hurts when low-quality pipelines are included."* This is a more nuanced version of RQ9 that survives the data.

4. **The top-1 result reveals a calibration insight.** Top-1 ensemble = BITEM_sonnet's answer with confidence=100 on every non-refused topic, rather than Variant A's average ~89 confidence. **HMR jumps from 0.963 → 0.974 just by maxing confidence.** Why? When a pipeline's accuracy on its non-refused topics is 100% (as BITEM_sonnet's is), R_U is *literally penalised* by under-confidence. **HMR rewards accuracy-aligned confidence**: if you know a system answers correctly when it answers at all, give it max confidence.

5. **The non-monotonic curve (top-1 best → top-2 worse → top-3 strong → top-4 drops) supports a "wisdom only from selected experts" reading.** Adding the second BITEM variant (broad) introduces correlated noise; adding a third *different-pool* voter (tier1_sonnet) provides genuinely independent signal that helps. After that, additional pipelines bring more disagreement than information.

6. **R_O is invariant at 0.950 across top-1/2/3 and at 0.95 for top-12** — high-quality voters don't disagree on the easy topics; the variance is in R_U (under-confidence on cases of partial agreement).

**Implication for submission.** The new top-2 candidates are:
- **ensemble_top1** (HMR 0.974) — essentially BITEM_sonnet with perfect confidence
- **ensemble_top3** (HMR 0.969) — small bonus from adding tier1_sonnet's vote

### RQ10 — Pipeline LLM tier sensitivity (2026-05-05, COMPLETED)

Ran a 5-variant ablation on BITEM_only pool, swapping Sonnet → Haiku at each pipeline stage individually. Self-eval always Sonnet (mimics organizer judge).

**Per-stage cost-quality table:**

| Variant | Stage 1 | Stage 1.5 | Stage 2 | Stage 4 | Acc | MNP | R_O | R_U | HMR | ΔHMR |
|---|---|---|---|---|---|---|---|---|---|---|
| **all-Sonnet** (baseline) | S | S | S | S | 0.938 | 0.629 | 0.950 | 0.976 | **0.963** | 0 |
| **s4-Haiku** | S | S | S | H | 0.923 | 0.594 | 0.870 | 0.961 | 0.913 | **−0.050** |
| **s2-Haiku** | S | S | H | S | 0.908 | 0.669 | 0.850 | 0.953 | 0.899 | −0.064 |
| **s1-Haiku** | H | S | S | S | 0.892 | 0.549 | 0.750 | 0.945 | 0.836 | −0.127 |
| **all-Haiku** | H | H | H | H | 0.877 | 0.584 | 0.708 | 0.900 | 0.792 | −0.171 |

**Findings (4 paper-worthy results):**

1. **Stage 1 (candidate answer) is the MOST Sonnet-critical stage** at ΔHMR = −0.127. Reading 50 passages and producing a single confident answer requires Sonnet-level reasoning. R_O drops sharply (0.950 → 0.750) — Haiku produces less calibrated confidence on the answer it commits to.

2. **Stage 4 (verifier) is the LEAST Sonnet-critical** at ΔHMR = −0.050. Despite being the calibration source, Haiku here costs only 0.050 HMR. The verifier's task (deriving an answer from a few clean nuggets) is simpler than reading raw passages and benefits less from Sonnet.

3. **Stage 2 (nugget extraction) is moderately critical** at −0.064. R_O drops 0.950 → 0.850 (less calibrated nugget extraction) but accuracy and MNP hold up. Haiku can extract entailed nuggets but the surrounding answer quality suffers.

4. **All-Haiku at −0.171 is approximately additive** of the per-stage drops (0.127 + 0.050 + 0.064 + ~ε ≈ 0.241 vs observed 0.171), suggesting non-trivial interaction: stages compensate for each other partially. Sonnet-on-S1 alone almost recovers the full pipeline because a strong candidate answer cascades into better nugget targeting.

**Practical recipe for paper:**

> "Sonnet is necessary at Stage 1 (candidate answer) and beneficial at Stage 2 (nugget extraction); Haiku is sufficient for Stage 4 (verifier) and Stage 1.5 (refinement scoring) at minimal cost. A 'Sonnet on first half, Haiku on second half' hybrid achieves HMR within 0.05 of all-Sonnet at ≈40% the cost."

This is a falsifiable, replicable, deployable recommendation.

**Remaining cost question.** We didn't measure exact per-stage cost. To complete the cost-quality frontier rigorously we'd need to log token usage. For the paper, "Sonnet calls per stage" can be reported (already known from cache sizes).
